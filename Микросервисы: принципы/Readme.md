
# Домашнее задание к занятию «Микросервисы: принципы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.


### Решение для реализации API Gateway

API Gateway — это ключевой компонент в микросервисной архитектуре, который обеспечивает единую точку входа для всех клиентских запросов, маршрутизацию, аутентификацию, терминацию HTTPS и другие функции. Для реализации API Gateway можно рассмотреть несколько популярных решений:

1. **NGINX**  
2. **Kong**  
3. **Traefik**  
4. **AWS API Gateway**  
5. **Spring Cloud Gateway**  

### Сравнительная таблица возможностей

| Функция / Решение          | NGINX               | Kong                | Traefik             | AWS API Gateway     | Spring Cloud Gateway |
|----------------------------|---------------------|---------------------|---------------------|---------------------|----------------------|
| **Маршрутизация запросов** | Да                  | Да                  | Да                  | Да                  | Да                   |
| **Аутентификация**         | Базовая (с плагинами) | Да (с плагинами)    | Да (с плагинами)    | Да                  | Да (с интеграцией)   |
| **Терминация HTTPS**       | Да                  | Да                  | Да                  | Да                  | Да                   |
| **Поддержка микросервисов**| Ограниченная        | Да                  | Да                  | Да                  | Да                   |
| **Интеграция с облаком**   | Нет                 | Да (с плагинами)    | Да                  | Да (AWS)            | Да (Spring Cloud)    |
| **Простота настройки**     | Средняя             | Высокая             | Высокая             | Высокая             | Средняя              |
| **Масштабируемость**       | Высокая             | Высокая             | Высокая             | Высокая             | Высокая              |
| **Поддержка плагинов**     | Ограниченная        | Да                  | Да                  | Ограниченная        | Да                   |
| **Стоимость**              | Бесплатно           | Бесплатно (Open Source) | Бесплатно         | Платная             | Бесплатно            |

### Выбор решения

На основе таблицы и требований, лучшим выбором будет **Kong**. Вот обоснование:

1. **Маршрутизация запросов**: Kong предоставляет гибкую и мощную систему маршрутизации, которая легко настраивается через конфигурации.
2. **Аутентификация**: Kong поддерживает множество плагинов для аутентификации, таких как JWT, OAuth2, Key Auth и другие.
3. **Терминация HTTPS**: Kong поддерживает терминацию HTTPS из коробки.
4. **Поддержка микросервисов**: Kong изначально разработан для работы в микросервисной архитектуре.
5. **Простота настройки**: Kong имеет удобный интерфейс и API для управления конфигурациями.
6. **Масштабируемость**: Kong легко масштабируется и может работать в кластерной конфигурации.
7. **Плагины**: Широкая поддержка плагинов позволяет расширять функциональность Gateway.
8. **Стоимость**: Kong доступен как Open Source решение, что делает его экономически выгодным.

### Альтернативы

- **NGINX**: Подходит для простых сценариев, но требует больше ручной настройки и менее гибок в плане интеграции с микросервисами.
- **Traefik**: Хороший выбор для облачных сред, но менее зрелый по сравнению с Kong.
- **AWS API Gateway**: Отличное решение для использования в экосистеме AWS, но может быть дорогим и менее гибким для локальных решений.
- **Spring Cloud Gateway**: Подходит для проектов на Spring, но требует больше усилий для настройки и интеграции.

Таким образом, **Kong** является наиболее сбалансированным решением, удовлетворяющим всем требованиям.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

### Решение для выбора брокера сообщений

Брокер сообщений — это ключевой компонент в системах, где требуется асинхронная обработка сообщений, обеспечение надёжности и масштабируемости. Рассмотрим несколько популярных решений:

1. **Apache Kafka**  
2. **RabbitMQ**  
3. **Apache ActiveMQ**  
4. **NATS**  
5. **Redis (Pub/Sub)**  

### Сравнительная таблица возможностей

| Функция / Решение          | Apache Kafka        | RabbitMQ            | Apache ActiveMQ     | NATS                | Redis (Pub/Sub)      |
|----------------------------|---------------------|---------------------|---------------------|---------------------|----------------------|
| **Кластеризация**           | Да                  | Да                  | Да                  | Да                  | Да (с Redis Cluster) |
| **Хранение на диске**       | Да                  | Да                  | Да                  | Нет                 | Нет                  |
| **Скорость работы**         | Очень высокая       | Высокая             | Средняя             | Очень высокая       | Очень высокая        |
| **Поддержка форматов**      | Любые (бинарные)    | Любые               | Любые               | Любые               | Любые                |
| **Разделение прав доступа** | Да (с плагинами)    | Да                  | Да                  | Нет                 | Нет                  |
| **Простота эксплуатации**   | Средняя             | Высокая             | Средняя             | Высокая             | Высокая              |
| **Надёжность**              | Очень высокая       | Высокая             | Высокая             | Высокая             | Средняя              |
| **Масштабируемость**        | Очень высокая       | Высокая             | Средняя             | Высокая             | Высокая              |
| **Стоимость**               | Бесплатно           | Бесплатно           | Бесплатно           | Бесплатно           | Бесплатно            |

### Выбор решения

На основе таблицы и требований, лучшим выбором будет **Apache Kafka**. Вот обоснование:

1. **Кластеризация**: Kafka поддерживает кластеризацию из коробки, что обеспечивает высокую надёжность и отказоустойчивость.
2. **Хранение на диске**: Kafka хранит сообщения на диске, что гарантирует их сохранность даже в случае сбоев.
3. **Скорость работы**: Kafka обеспечивает очень высокую скорость обработки сообщений, что важно для высоконагруженных систем.
4. **Поддержка форматов**: Kafka работает с бинарными данными, что позволяет передавать сообщения любого формата.
5. **Разделение прав доступа**: Kafka поддерживает разделение прав доступа через плагины, такие как Kafka ACL.
6. **Простота эксплуатации**: Хотя Kafka требует определённых усилий для настройки, её эксплуатация в кластерной среде хорошо документирована и поддерживается.
7. **Надёжность**: Kafka обеспечивает очень высокую надёжность благодаря репликации данных и кластеризации.
8. **Масштабируемость**: Kafka легко масштабируется как горизонтально, так и вертикально.

### Альтернативы

- **RabbitMQ**: Хороший выбор для систем с менее жёсткими требованиями к скорости и объёмам данных. Прост в настройке и эксплуатации.
- **Apache ActiveMQ**: Подходит для систем, где требуется поддержка JMS, но уступает Kafka в производительности и масштабируемости.
- **NATS**: Отличный выбор для систем, где важна скорость и низкая задержка, но отсутствует хранение сообщений на диске.
- **Redis (Pub/Sub)**: Подходит для простых сценариев с низкими требованиями к надёжности и сохранности сообщений.

Таким образом, **Apache Kafka** является наиболее подходящим решением для задач, требующих высокой надёжности, скорости и масштабируемости.

## Задача 3: API Gateway * (необязательная)

### Есть три сервиса:

**minio**
- хранит загруженные файлы в бакете images,
- S3 протокол,

**uploader**
- принимает файл, если картинка сжимает и загружает его в minio,
- POST /v1/upload,

**security**
- регистрация пользователя POST /v1/user,
- получение информации о пользователе GET /v1/user,
- логин пользователя POST /v1/token,
- проверка токена GET /v1/token/validation.

### Необходимо воспользоваться любым балансировщиком и сделать API Gateway:

**POST /v1/register**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/user.

**POST /v1/token**
1. Анонимный доступ.
2. Запрос направляется в сервис security POST /v1/token.

**GET /v1/user**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис security GET /v1/user.

**POST /v1/upload**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис uploader POST /v1/upload.

**GET /v1/user/{image}**
1. Проверка токена. Токен ожидается в заголовке Authorization. Токен проверяется через вызов сервиса security GET /v1/token/validation/.
2. Запрос направляется в сервис minio GET /images/{image}.

### Ожидаемый результат

Результатом выполнения задачи должен быть docker compose файл, запустив который можно локально выполнить следующие команды с успешным результатом.
Предполагается, что для реализации API Gateway будет написан конфиг для NGinx или другого балансировщика нагрузки, который будет запущен как сервис через docker-compose и будет обеспечивать балансировку и проверку аутентификации входящих запросов.
Авторизация
curl -X POST -H 'Content-Type: application/json' -d '{"login":"bob", "password":"qwe123"}' http://localhost/token

**Загрузка файла**
