<h2>
5. Опишите основные плюсы и минусы pull и push систем мониторинга.
</h2>

<h3>Pull-системы мониторинга</h3>

#
<h4>Плюсы:</h4>

Централизованное управление: Сервер мониторинга сам запрашивает данные с агентов или экспортеров, что упрощает управление и настройку.
#
Масштабируемость: Легче масштабировать, так как сервер может контролировать частоту опроса и нагрузку на агенты.
#
Безопасность: Агенты не открывают порты для входящих соединений, что снижает поверхность атаки.
#
Гибкость: Можно легко добавлять или удалять агенты без изменения конфигурации сервера.
#
Отсутствие потери данных: Если агент временно недоступен, сервер может повторить запрос позже.

<h4>Минусы:</h4>

Задержки: Данные собираются только в момент опроса, что может привести к задержкам в обнаружении проблем.
#
Нагрузка на сеть: При большом количестве агентов и высокой частоте опросов может возникать нагрузка на сеть.
#
Сложность в динамических средах: В облачных или контейнеризированных средах, где IP-адреса и хосты часто меняются, управление pull-запросами может быть сложным.
#
Зависимость от сервера: Если сервер мониторинга недоступен, данные не будут собраны.

<h3>Push-системы мониторинга</h3>

<h4>Плюсы:</h4>

Оперативность: Агенты отправляют данные сразу при их появлении, что позволяет быстрее реагировать на изменения.
#
Поддержка динамических сред: Подходит для облачных и контейнеризированных сред, где агенты могут самостоятельно регистрироваться и отправлять данные.
#
Гибкость в отправке данных: Агенты могут отправлять данные на несколько серверов или в разные системы мониторинга.
#
Меньшая нагрузка на сервер: Сервер не занимается опросом агентов, что снижает нагрузку на него.

<h4>Минусы:</h4>

Сложность управления: Требуется настройка агентов для отправки данных на правильные серверы.
#
Безопасность: Агенты должны открывать исходящие соединения, что может быть нежелательно в некоторых сетевых конфигурациях.
#
Потеря данных: Если сервер недоступен, данные могут быть потеряны, если агенты не имеют буферизации.
#
Масштабируемость: При большом количестве агентов сервер может быть перегружен входящими данными.
#
Сложность отладки: Труднее диагностировать проблемы, если агенты не отправляют данные или отправляют их некорректно.

<h3>Итоговое сравнение:</h3>

Pull лучше подходит для статических сред, где важна централизация и безопасность.
#
Push предпочтителен в динамических средах, где важна оперативность и гибкость.

<h3>На практике часто используются гибридные подходы, сочетающие преимущества обеих систем. Например, Prometheus использует pull-модель, но поддерживает push через шлюз (Pushgateway) для временных задач</h3>

```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в
