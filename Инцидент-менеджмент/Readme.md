Информацию о сбое можно изучить по ссылкам ниже:

**Постмортем: Сбой системы GitHub 21 октября 2018 года**

**Краткое описание инцидента**  
21 октября 2018 года GitHub, одна из крупнейших платформ для хостинга кода и совместной разработки, столкнулась с масштабным сбоем, который длился около 24 часов. Инцидент был вызван проблемами в распределенной базе данных, что привело к нарушению работы ключевых сервисов, включая веб-интерфейс, API и операции с Git (pull, push и другие).

---

**Хронология событий**  
1. **Начало инцидента (21 октября, 22:52 UTC)**  
   - Инженеры GitHub обнаружили неполадки в работе кластера базы данных MySQL, используемого для хранения метаданных репозиториев, issue, pull request и других данных.  
   - Произошла деградация производительности, что привело к увеличению задержек и ошибкам при обработке запросов.

2. **Эскалация (22 октября, 00:05 UTC)**  
   - Проблемы с базой данных усугубились, что привело к полной недоступности некоторых сервисов.  
   - Команда GitHub начала расследование и попыталась восстановить работоспособность системы.

3. **Попытки восстановления**  
   - Инженеры предприняли несколько попыток восстановить работу базы данных, включая перезапуск серверов и репликацию данных.  
   - Однако эти действия не принесли ожидаемого результата, так как проблемы были связаны с внутренними процессами оркестрации и синхронизации данных.

4. **Полное восстановление (22 октября, 23:00 UTC)**  
   - После длительного анализа и тестирования команде GitHub удалось стабилизировать работу базы данных и восстановить все сервисы.  
   - Платформа вернулась к нормальной работе, хотя некоторые пользователи могли наблюдать задержки в течение следующих нескольких часов.

---

**Причины сбоя**  
Основной причиной инцидента стала **некорректная работа оркестратора базы данных**, который управлял топологией кластера MySQL. В частности:  
1. Оркестратор неправильно обработал изменение топологии, что привело к рассогласованию данных между узлами.  
2. Это вызвало каскадный эффект, включая потерю данных и невозможность синхронизации между репликами.  
3. Попытки вручную исправить ситуацию усугубили проблему, так как команда не сразу смогла определить корневую причину.

---

**Последствия**  
- **Для пользователей**:  
  - Невозможность использовать ключевые функции GitHub, включая push/pull-запросы, создание issue и просмотр репозиториев.  
  - Задержки в работе платформы даже после восстановления.  

- **Для GitHub**:  
  - Потеря доверия со стороны пользователей, особенно корпоративных клиентов.  
  - Необходимость пересмотра процессов мониторинга и восстановления баз данных.  

---

**Уроки и улучшения**  
GitHub опубликовал подробный постмортем, в котором описал шаги, предпринятые для предотвращения подобных инцидентов в будущем:  
1. **Улучшение мониторинга**: Внедрение более детального мониторинга состояния оркестратора и базы данных.  
2. **Тестирование отказоустойчивости**: Регулярное проведение тестов на отказоустойчивость и восстановление.  
3. **Обновление процессов**: Пересмотр процедур ручного вмешательства в работу баз данных для минимизации рисков.  
4. **Прозрачность**: Улучшение коммуникации с пользователями во время инцидентов.  

---

**Заключение**  
Сбой GitHub в октябре 2018 года стал важным уроком для индустрии, подчеркнув сложность управления распределенными системами и важность надежных процессов восстановления. Компания продемонстрировала высокий уровень прозрачности, опубликовав детальный постмортем, что помогло укрепить доверие сообщества.
